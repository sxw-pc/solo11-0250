# 服务依赖启动协同台

离线微服务冷启动控制面模拟。使用 Python 3.11+ 标准库、SQLite 和本地探针事件；不启动容器，也不处理版本发布。

## 三个入口

- `contract`：服务修订、依赖边和启动令牌。封存依赖图前检查循环；关键上游缺席时，限时降级授权可单独改变启动结论。上游撤回后可重新裁定下游契约。
- `wave`：启动波次、节点启动槽和尝试代次。槽容量、令牌代次、上游就绪回执和期限共同决定是否下发；超时释放槽，迟到成功不能重用旧尝试。
- `ready`：探针样本、就绪回执和级联回滚案。仅当前尝试时间窗内的最新连续健康样本、当前服务修订和关键上游回执可发布就绪；上游撤回传播到下游。

业务实体分属不同表，所有写入通过 IMMEDIATE 事务。原始事件、业务裁决和完整状态可重放核对。

## 运行

```sh
python -m cloudcourt demo --db demo.sqlite
python -m cloudcourt replay --db demo.sqlite
python -m unittest discover -s tests -v
```

每个入口各有 `fixtures/<入口>-normal.json` 和 `-failure.json`。`fixtures/path.json` 在数据库服务启动后先发布上游就绪，再下发 API 服务启动波次。独立命令例如 `python -m cloudcourt contract --db state.sqlite --fixture fixtures/contract-normal.json`；跨入口运行时复用同一个新数据库。

测试覆盖依赖环、槽容量、旧代令牌、限时降级、探针迟到、上游回执撤销与下游回滚。关键业务结果通过 `readiness_receipts`、`boot_waves` 和 `rollback_cases` 观察，不仅看命令退出码。

降级就绪回执记录许可的最早到期时刻；`ready expire` 会撤销到期回执并传播到后继服务。启动尝试绑定节点槽代次，节点重建后旧探针不能发布就绪。服务修订换代会清除旧修订的依赖边。

## 冷启动热暴露与设备适用性裁决

`thermal` 在原 `zone`/`sample`/`check` 单点判定之外，增加面向设备的累计热剂量裁决，命令走同一事件日志、同一重放核对：

- 每个温度原件锁定传感器序列号、入口/排气/近芯片位置、节点序列号、采样时窗和测量不确定度；迟到校准以追加行保留修订依据，原始读数永不改写。
- 热暴露按 `start_attempts` 的启动、预热、稳定运行真实时间窗积分：活读数间线性插值，传感器断线与跨波次间隙按冷却惯性指数回落。每台设备取最差探头的低/高剂量带，远离热点的低温探头不能抵消近芯片超温；剂量带跨越制造商上限即判 `indeterminate`，必须把不可判定区间告知客户。
- 传感器断线、近芯片单点超过制造商最高运行温度都会阻止出具合格结论；新健康探针或单条低温样本不能自动解除限制。
- 设备适用结论只追加复核（`device_fitness_reviews`），受疑使用时段（`suspect_use_periods`）在限制解除前保留开放区间，客户此前使用受疑设备的历史不被擦掉。
- 三种处置各自记录实测条件、客户可用容量与保修责任：`derated`（持续监测下限功率、条件保修、较早获得较低容量）、`reinspect_shutdown`（停机零容量、完整保修、复检通过才恢复）、`replaced`（更换疑似受损部件、硬件费用、较晚恢复容量、备件完整保修）。复检失败路由制造商保修并要求更换。
- `thermal_case_items` 把受影响的 `node_thermal_checks`、启动尝试、容量契约、制造商证明、处置与保修记录逐项对应到同一暴露案。

`fixtures/thermal-exposure.json` 是双探头冷启动端到端场景：节点 N 入口 36°C、近芯片原始 46°C（带可查校准偏差），制造商剂量上限落在修正误差区间内，独立检查无永久损伤，并覆盖传感器断线、相邻波次叠加、迟到校准、复检失败与更换部件；验收见 `tests/test_thermal_exposure.py`。
